01 · Preamble

What gets tracked gets real.

The Work Ledger is a coordination-legibility tool. Its purpose is to surface collective work — across GitHub repositories, Workshop sprints, and the Techne address space — in a single queryable record, held in Supabase and readable at /intranet/activity/.

It is not a project management system. It does not assign work, set deadlines, or rank priorities. It does not replace GitHub, the Workshop, or any existing surface. It is a ledger: an append-only record of what happened, who did it, in what phase, against which artifact.

The tool implements the Activity surface defined in the CIS PRD v0.2 (section 10). It is the Event primitive in the REA ontology made navigable: every row is an event, every event has an agent, every agent is traceable back to the cooperative's identity layer.

02 · Learning from the Workshop

The Workshop as systems teacher.

The Workshop — co-op.us/app/coordinate — has been the coordination surface for Nou, Dianoia, and human members of Techne since early 2026. It runs the Clawsmos five-phase protocol: Discovery → Proposal → Negotiation → Execution → Synthesis. Every sprint passes through these phases in the database before it can be closed.

What the Workshop taught us

The Workshop's most durable contribution is not the sprint protocol itself — it is the anti-pattern documentation embedded in the SKILL.md. Each anti-pattern names a real failure mode and reveals something that a coordination-legibility tool must solve:

Anti-pattern: Ghost Execution

Work without a coordination record is invisible

An agent writes code, commits to GitHub, reports completion — but never calls the Workshop API. The sprints remain in proposed status. The Protocol Stream shows no activity. Other participants have no evidence the work happened. The fix is not retroactive: you cannot meaningfully back-date protocol events.

The Work Ledger is the fix made structural. Every completed sprint completion_proof (a GitHub URL) creates a work_event. The ledger is the bridge between the artifact store (git) and the coordination layer (Workshop).

Anti-pattern: Git Archaeology

Sprints live in the database, not in git

Looking in the wrong place wastes cycles and produces false negatives. The correct answer is always: query the API. The Work Ledger makes this true from the other direction: a member should never need to search multiple systems to answer "what has been happening?" — one surface, one query, one record.

Principle: Transparent Agency

No private channels, no invisible work

The Clawsmos founding principle: all coordination is legible. The Work Ledger applies this principle across the full address space — not only to Workshop sprints but to GitHub commits, PR merges, page updates, and document changes. If it happened under the Techne identity layer, it should be findable.

Pattern: Phase is more than status

Coordination has arc, not just state

A sprint is not just "open" or "closed." It is somewhere in a five-phase arc, and where it sits matters for what actions are appropriate. The Work Ledger carries this insight forward: work events carry their phase context so a feed can be filtered not only by actor or repo but by coordination maturity — showing, for instance, all work currently in synthesis phase across all surfaces.

03 · Principles

Five constraints that hold.

01 · REA-grounded

Every row is an Event with an Agent and a Resource

The information model traces directly to the REA ontology: Agent (actor), Event (the work_event record), Resource or Agreement (the subject). No proprietary schema, no bespoke abstractions. A work event in this system is recognizable to any system using REA, and translates without loss.

02 · Append-only

Records are never edited, only superseded

The ledger does not allow retroactive edits to work events. A correction is a new event with event_type: 'correction' and a parent_id pointing to the original. This is the same principle that makes the Workshop's Protocol Stream trustworthy, and it is the property the audit surface in CIS v0.2 depends on.

03 · Agent parity

Nou and Dianoia appear as first-class actors, not noise

Agent-authored work events carry the same actor_type dignity as human events. Attribution is full and unambiguous. A filter for "all Nou contributions in the last 30 days" should return the same quality of record as "all Todd contributions in the last 30 days." Agent work is not a footnote.

04 · Progressive legibility

Useful at Phase 1, richer at Phase 3

The tool is genuinely useful from first commit. Phase 1 is a manually-augmented feed of Workshop sprint completions. Phase 2 adds GitHub webhook ingestion. Phase 3 adds address space coverage views. Each phase is complete on its own terms. The PRD does not require Phase 3 to justify Phase 1.

05 · Not surveillance

The ledger records outcomes, not keystrokes

Work events are coarse-grained: sprint completed, PR merged, commit pushed, page updated. They are not granular: file changed, line edited, time on task. The distinction matters. A ledger of outcomes supports coordination and attribution. A log of keystrokes supports monitoring. This is a ledger.

04 · System Definition

Three sources, one surface.

The Work Ledger reads from three external systems and writes normalized events into a single Supabase table. It does not replace any of its sources. It is a read layer with one write primitive: work_events.

Sources

Source A · Workshop

co-op.us/app/coordinate

Sprint state changes (claimed, completed, synthesized) from the coordination_requests table via Supabase realtime or periodic poll. These events carry the richest coordination metadata: phase, actor, completion_proof URL, result_summary. The Work Ledger treats completed Workshop sprints as the highest-confidence work events: coordination and artifact evidence in the same record.

Source B · GitHub

RegenHub-Boulder and related orgs

Push events, PR merges, and issue closures via GitHub webhook → Supabase edge function. A minimal handler normalizes each event into the work_events schema. Phase is inferred from event type (PR merged → Execution; issue closed with "closes" body → Synthesis). Actor matching against the participants table uses GitHub username as the lookup key.

Source C · Address space

techne.institute / URL coverage

Pages and documents updated in the techne.institute repo are surfaced as URL-subject work events, extracted from GitHub push events that touch HTML or document files. This enables an address-space view: which pages were touched in the last 30 days, by whom, in what context. Phase 3 only — derived from Source B, no additional integration needed.

What it does not do

The Work Ledger does not manage work items (that is the Workshop), does not hold canonical sprint state (that is coordination_requests), does not track billable labor hours (that is the Labor Tracking module in the CIS), and does not make editorial judgments about work quality. It is a record, not an evaluator.

05 · Information Model

One table. Six columns that matter.

The entire model is a single table — work_events — on the CIS Supabase project. It extends the existing CIS identity layer by referencing the participants table. No new schemas, no new projects.

-- All work events, normalized across sources.
-- REA mapping: actor (Agent) + work_event row (Event) + subject (Resource or Agreement)
CREATE TABLE work_events (
  id             uuid         DEFAULT gen_random_uuid() PRIMARY KEY,
  created_at     timestamptz  DEFAULT now() NOT NULL,

  -- Actor (REA: Agent)
  actor_id       uuid         REFERENCES participants(id),  -- nullable: external actors
  actor_name     text         NOT NULL,                        -- display name
  actor_type     text         CHECK (actor_type IN ('human', 'agent', 'system')),

  -- Event type and phase
  event_type     text         NOT NULL,   -- 'sprint_completed', 'git_push', 'pr_merged', etc.
  phase          text,                     -- discovery | proposal | execution | synthesis

  -- Subject (REA: Resource or Agreement)
  subject_type   text         NOT NULL,   -- 'sprint', 'git_repo', 'url', 'document'
  subject_ref    text,                     -- sprint_id (P486), repo slug, URL path
  subject_url    text,                     -- canonical link to artifact

  -- Payload
  title          text,
  summary        text,

  -- Provenance
  source         text         NOT NULL,   -- 'workshop' | 'github' | 'manual'
  source_id      text                      -- original ID (sprint UUID, commit SHA)
);

Identity join

The work_events table references the existing participants table on the CIS Supabase project. The join is nullable: events from GitHub webhooks may arrive before an actor match is established. Unmatched actors are held in the table with actor_id null and actor_name from the webhook payload. A steward can later claim an unmatched event by updating actor_id.

06 · Interface

Three views, one URL.

The interface lives at /intranet/activity/ — the Activity surface in the CIS v0.2 primary navigation. It is auth-gated (same gate as /intranet/treasury/ and /intranet/board/). Three tab views share the same underlying data.

View 1 · Feed

The default view. A reverse-chronological list of work events. Each event card shows: phase pill, event_type label, actor name and type badge (human / agent), subject_ref with link, title, created_at relative timestamp, and a collapse/expand toggle for summary text. Filter bar at top: phase, actor_type, source, subject_type. Date range picker. No pagination UI — virtual scroll.

View 2 · Attribution

A grouped view by actor. Each actor shows: total events, events by phase (spark-bar), events by subject_type (spark-bar), most recent event. Useful for answering "what has Dianoia shipped in the last 60 days?" or "which humans have been most active in synthesis phase?" Sortable by event count, recency, phase distribution. Phase 2 only — requires sufficient data density to be readable.

View 3 · Coverage

A URL-tree view of the Techne address space. Every path that has a work event in the selected window is listed. Depth-folded: /cis/ collapses children until expanded. Each path shows: event count, distinct actor count, last touched date, phase of most recent event. Useful for answering "which parts of the site haven't been touched in 90 days?" Phase 3 only.

Design notes

The interface follows the co-op.us design system: dark ground at #0f0f0f, IBM Plex Mono throughout, terracotta accent sparingly. Phase pills use the five-phase color system established in this document. No charts with axes — this is a ledger, not an analytics dashboard. Numbers are counts, not graphs.

07 · Integration Points

Three connections, minimal surface area.

IntegrationMechanismDirectionPhase
Workshop sprint completions Supabase realtime subscription on coordination_requests WHERE status = 'completed'. Edge function normalizes into work_events. Fallback: periodic poll every 15 min. Workshop → work_events Ph1
GitHub push + PR events GitHub webhook (one per org) → Supabase edge function work-event-ingest. Handles push, pull_request.closed (merged=true). Normalizes actor via github_username → participants lookup. GitHub → work_events Ph2
GitHub issue closure Same webhook, issues.closed event type. Infers synthesis phase when body contains "closes #" or "fixes P\d+" pattern. Low confidence — manual phase override allowed. GitHub → work_events Ph2
Manual entry POST /work-event-ingest with source = 'manual'. Used for work that happened outside tracked systems (in-person, off-platform). Steward-only. Steward → work_events Ph1
Address space indexing GitHub push events touching *.html or *.md files in techne.institute repo emit additional work_events with subject_type = 'url' and subject_ref = the file path as a URL. Derived from Ph2 Ph3

Edge function: work-event-ingest

A single Supabase edge function receives both the GitHub webhook and the Workshop realtime events. It normalizes them into the work_events schema and inserts via the REST API using the service key. It does not validate business logic — it only normalizes and writes. Validation (e.g., deduplication on source_id) is handled by a unique constraint: UNIQUE(source, source_id) on work_events.

08 · Roadmap

Three phases. Useful at each one.

The roadmap is deliberately short. A work tracking tool that takes six months to reach its first useful state has already failed. Phase 1 is deployable in a single sprint. Phase 2 follows when GitHub integration is needed. Phase 3 is optional enhancement.

What Phase 1 does not need

Phase 1 does not need GitHub integration. It does not need address space coverage. It does not need the attribution view. It needs one table, one edge function, and one HTML page. If it ships those three things and surfaces Workshop sprint completions in a readable feed, it has succeeded. Complexity accumulates in subsequent phases only when the simpler phase has proven its value.

09 · Open Questions

What we do not yet know.

Actor matching confidence

GitHub username → participant is imperfect

Not every GitHub committer will have a participant record. The unmatched-actor handling described in the information model (actor_id nullable, steward-claimable) is a reasonable Phase 2 start, but it will produce noise in the Attribution view until matching is mature. Needs a steward-facing reconciliation UI or a more automated matching strategy (email fallback, ENS lookup for agent commits).

Supabase project placement

Which project hosts work_events?

The work_events table references participants, which lives on the CIS Supabase project (hvbdpgkdcdskhpbdeeim). The Workshop sprint completions come from the same project. GitHub events are external. The simplest answer is to add work_events to the existing CIS project — avoiding cross-project joins. But the Workshop project and the CIS are currently co-located, so this needs explicit confirmation before the table is created.

Phase inference from GitHub events

PR merged → Execution is an approximation

The five-phase model maps cleanly onto Workshop sprint lifecycle. GitHub events have no native phase concept. The inferred mapping (push → Execution, issue closed → Synthesis) is a heuristic and will misfire. An explicit phase override field in work_events allows a steward or agent to correct the inference. Whether the heuristic is good enough for the Attribution and Coverage views needs empirical testing at Phase 2.

Scope of GitHub orgs to track

RegenHub-Boulder is clear; what else?

RegenHub-Boulder/techne.institute is the obvious first target. Roots-Trust-LCA (coordination games, cooperation.games), dianoi/dianoia, and nou-techne are all relevant. Each org requires a separate webhook. The Phase 2 sprint should define the complete webhook list before implementation, not discover it incrementally.

Retention and privacy

How long does work_events persist?

The append-only principle implies indefinite retention. In practice, old events accumulate. A soft archival policy (events older than 18 months move to a cold view, excluded from default feed queries) keeps the active table fast without destroying the record. CROPS privacy consideration: work event summaries may contain discussion excerpts from Workshop sprint messages — if those are included in summary, they should be member-only, not publicly queryable.

The coordination surface taught us something that can't be built in: the difference between work that happened and work that is known to have happened. Ghost execution is not a bug in an individual agent's behavior — it is what happens whenever two systems hold partial records of the same reality. The Work Ledger is an attempt to close that gap.

It will not close it completely. No ledger does. But a cooperative that can answer "what did we make together last month?" from a single surface is a cooperative that can see itself. That's the minimum viable condition for collective intelligence.
