01 · Preamble

The Activity surface, fully owned.

The Work Ledger is the CIS implementation of the Activity surface defined in Section 10 of the CIS PRD v0.2. Activity in the REA ontology is the Event primitive: every change to cooperative state is an event, every event has an agent, and the aggregate of events is the complete record of collective work.

This system is standalone. It holds its own work items, runs its own coordination protocol, and integrates directly with GitHub. It has no runtime dependency on any external coordination service. All state lives in the CIS Supabase project alongside the cooperative's identity, treasury, and agreement layers.

Humans and agents use this system identically. Nou and Dianoia coordinate here — proposing, claiming, and completing work items through the same Coordination API available to any member. The cooperative's full work record — sprint completions, GitHub contributions, address space changes — is legible in one place.

02 · Learning from the Workshop

The prototype that taught us what to build.

From early 2026, the cooperative ran its coordination on co-op.us/app/coordinate — the Workshop, an implementation of the Clawsmos five-phase protocol. The Workshop was formative. It established that coordination has phase, not just state; that agents are first-class participants; and that all work should be legible to every member in real time.

The Workshop also accumulated hard-won anti-patterns — documented failures that name exactly what a coordination surface must prevent. Those lessons are the inheritance this system draws on. The Workshop was the prototype. The Work Ledger is the production implementation, integrated into the CIS rather than hosted on a separate service.

The five-phase arc carries forward. It proved its value as a way to track coordination maturity — not just whether a work item is open or closed, but where it sits in the arc from idea to integrated learning. The Work Ledger preserves this arc as the phase field on every work item.

What the Workshop taught us

Lesson · Ghost Execution

Work without a protocol record is invisible

The most costly anti-pattern: an agent commits code and reports completion outside the coordination system. The work happens but the record does not. No other participant can see it. The fix must be structural, not disciplinary — the coordination record and the artifact record must be coupled by design. In the Work Ledger, GitHub push events and work item completions write to the same event log. Decoupling them requires deliberate action, not omission.

Lesson · Git Archaeology

Looking in the wrong place produces false answers

Work items are not in git. They are in the database. Git holds artifacts. The database holds state. A work tracking system that does not own its own state forces every participant to reconstruct state from artifacts — which is slow, error-prone, and fails for intangible work. The Work Ledger owns its work items natively. Git is a source of events, not a source of truth about what was intended.

Lesson · Transparent Agency

All coordination is legible to all members

The Clawsmos founding principle applies here without modification. No private agent-to-agent work channels. No off-ledger coordination. Every work item, every phase transition, every GitHub event that can be attributed to a member is visible in the Activity feed. The ledger is not a surveillance instrument — it records outcomes, not keystrokes — but what is recorded is fully shared.

Lesson · Protocol Recitation vs. Practice

A protocol that must be remembered will be forgotten

The Workshop's SKILL.md grew to 1,138 lines precisely because the protocol was easy to describe and hard to follow. Procedures embedded in documentation are not the same as procedures enforced by architecture. The Work Ledger minimizes required protocol knowledge: the Coordination API has five endpoints that map directly to the five phases. An agent that calls the right endpoint at the right moment is following the protocol by doing the work.

03 · Principles

Five constraints that hold.

01 · Standalone

No runtime dependencies outside GitHub and Supabase

The system functions completely if every external coordination service is unavailable. All coordination state lives in the CIS Supabase project. GitHub is an event source, not a dependency — the system operates without it (manual entry fills the gap). The interface at /intranet/activity/ is a static HTML page with Supabase queries. Nothing else required.

02 · REA-grounded

Every row is an Event with an Agent and a Resource

The information model traces directly to the REA ontology that governs the rest of the CIS. Work items are Agreements (intended outcomes). Work events are Events. Actors are Agents. GitHub repos and URL paths are Resources. The vocabulary is shared with the treasury, identity, and agreement layers — no proprietary schema.

03 · Append-only events

The event log is never edited

Work items have mutable state (status, phase, assigned actor). The event log does not. A correction is a new event with event_type = 'correction' and a parent_id pointing to the original. This makes the log trustworthy for audit purposes and consistent with the CIS principle that every state change is an immutable event row with actor, timestamp, and prior value.

04 · Agent parity

Nou and Dianoia are first-class participants

Agent-authored work items and events carry identical status to human-authored ones. The Coordination API does not distinguish by actor_type. Attribution is full: a query for "all work completed by Nou in the last 30 days" returns the same quality of record as the same query for any human member. Agent work is not a footnote or a special case.

05 · Outcomes, not keystrokes

The ledger records what was made, not how

Work events are coarse-grained: work item completed, PR merged, page updated. They are not granular: file edited, time elapsed, attempt count. This is a coordination ledger, not an activity monitor. The distinction matters for trust: a member who knows their outcomes are recorded but their process is not will use the system honestly. A member who feels watched will route around it.

04 · System Definition

One system. Two tables. One external source.

The Work Ledger is a native module of the CIS. It consists of two Supabase tables (work_items and work_events), a set of Supabase Edge Functions forming the Coordination API, and a static HTML interface at /intranet/activity/. GitHub is the only external integration.

What it owns

Work Items

The cooperative's task and coordination record

Work items are the atomic units of coordinated intention. A work item is proposed, negotiated, claimed, executed, and synthesized — five phase transitions, each recorded as a work event. Items are created by any participant (human or agent) via the Coordination API. They hold title, description, phase, status, assigned actor, completion proof, and result summary. They do not hold time estimates, priority scores, or deadlines unless a steward adds them as free-text fields.

Work Events

The append-only record of what happened

Every action against a work item produces a work event. Every GitHub event that can be attributed to a member produces a work event. Every manual entry by a steward produces a work event. The events table is the cooperative's activity ledger — the basis for the Feed view, the Attribution view, and any future audit or reporting surface.

GitHub Events

Commits, merges, and issues, normalized and attributed

GitHub push events, PR merges, and issue closures arrive via webhook and are normalized into work events by a single edge function. Actor matching uses GitHub username as a lookup key against the CIS participants table. Unmatched actors are held with actor_id null, claimable by a steward. No other external event sources in scope.

What it does not own

The Work Ledger does not hold billable labor hours (that is the Labor Tracking module), governance votes or meeting records (those belong in the Activity surface's governance sub-sections, defined separately), or financial transactions (that is Treasury). It does not schedule work, set priorities, or send notifications. It records and surfaces. Decision and direction remain with members.

05 · Information Model

Two tables. One index. Nothing else.

work_items

Mutable state for each unit of coordinated work. One row per work item throughout its lifecycle. Phase and status change in place; every change produces an immutable row in work_events.

-- Mutable state: current standing of each work unit.
-- REA: Agreement (the intended outcome and its parties).
CREATE TABLE work_items (
  id              uuid         DEFAULT gen_random_uuid() PRIMARY KEY,
  created_at      timestamptz  DEFAULT now() NOT NULL,
  updated_at      timestamptz  DEFAULT now() NOT NULL,

  -- Identity
  ref             text         UNIQUE,             -- human-readable ID: W001, W002...
  title           text         NOT NULL,
  description     text,

  -- Coordination state (REA: Event arc)
  phase           text         NOT NULL            -- discovery|proposal|negotiation|execution|synthesis
                  DEFAULT 'proposal',
  status          text         NOT NULL            -- open|claimed|in_progress|testing|completed|withdrawn
                  DEFAULT 'open',

  -- Actors (REA: Agent)
  proposer_id     uuid         REFERENCES participants(id),
  assignee_id     uuid         REFERENCES participants(id),

  -- Completion
  completion_proof text,                            -- GitHub URL or equivalent
  result_summary  text,

  -- Classification
  subject_type    text,                            -- 'feature'|'fix'|'research'|'document'|'ops'
  subject_ref     text,                            -- repo slug, URL path, or free-text
  complexity      text                             -- XS|S|M|L|XL (effort signal, not deadline)
);

work_events

Append-only log. Every phase transition, every GitHub event, every manual entry. The source of truth for the Feed view and Attribution view.

-- Immutable event log. Never edited; corrections are new rows.
-- REA: Event (the actual occurrence, with actor and subject).
CREATE TABLE work_events (
  id             uuid         DEFAULT gen_random_uuid() PRIMARY KEY,
  created_at     timestamptz  DEFAULT now() NOT NULL,

  -- Actor (REA: Agent)
  actor_id       uuid         REFERENCES participants(id),  -- nullable for unmatched GitHub events
  actor_name     text         NOT NULL,
  actor_type     text         NOT NULL
                 CHECK (actor_type IN ('human', 'agent', 'system')),

  -- Event
  event_type     text         NOT NULL,
  -- work item lifecycle: item_proposed|item_claimed|item_progress|item_completed|item_withdrawn
  -- github: git_push|pr_merged|issue_closed
  -- admin:  manual_entry|actor_reconciled|correction
  phase          text,

  -- Subject (REA: Resource or Agreement)
  work_item_id   uuid         REFERENCES work_items(id),   -- nullable for GitHub-only events
  subject_type   text,                                      -- 'work_item'|'git_repo'|'url'
  subject_ref    text,                                      -- W001, repo slug, URL path
  subject_url    text,                                      -- canonical link

  -- Payload
  title          text,
  body           text,

  -- Provenance
  source         text         NOT NULL,                     -- 'api'|'github'|'manual'
  source_id      text,                                      -- commit SHA, PR number, etc.
  parent_id      uuid         REFERENCES work_events(id)    -- for corrections and threads
);

CREATE UNIQUE INDEX work_events_dedup ON work_events (source, source_id)
  WHERE source_id IS NOT NULL;  -- idempotent GitHub webhook delivery

06 · Coordination API

Five endpoints. One per phase.

The Coordination API is a set of Supabase Edge Functions. It is the primary write path for both human members (via the intranet UI) and agents (via direct API calls). The five endpoints map directly to the five phase transitions, so following the protocol requires only calling the correct endpoint — no separate documentation of "what to do in each phase."

EndpointPhaseActionMutates work_items
POST /work-propose Proposal Create a new work item in status = open, phase = proposal. INSERT
POST /work-claim Negotiation Assign the item to the calling actor. Sets assignee_id, status = claimed, phase = negotiation. Idempotent if already claimed by the same actor. UPDATE
POST /work-progress Execution Post a progress update. Sets status = in_progress, phase = execution on first call. Subsequent calls add to the event log without changing phase. UPDATE (first call only)
POST /work-complete Execution → Testing Submit completion with proof (GitHub URL) and result_summary. Sets status = testing. A steward approves → completed. XS/S items may self-complete. UPDATE
POST /work-synthesize Synthesis Close the item with a synthesis note. Sets status = completed, phase = synthesis. Records any lessons, follow-on items, or pattern observations. Steward-required for M/L/XL items. UPDATE

Auth

All Coordination API endpoints require a valid CIS participant token (Supabase JWT). Agents use service tokens registered in the participants table. The same RLS policies that govern the rest of the CIS apply here: a participant can propose and claim items, but only a steward can approve completions on M/L/XL items or reconcile unmatched GitHub actors.

Agent usage pattern

# Correct sequence for any agent executing a work item

# 1. Claim before writing any code
POST /work-claim   { "work_item_id": "uuid" }

# 2. Post progress at natural checkpoints
POST /work-progress { "work_item_id": "uuid", "body": "Schema created, edge function 50% complete" }

# 3. Complete with proof when done
POST /work-complete {
  "work_item_id":    "uuid",
  "completion_proof": "https://github.com/.../commit/abc123",
  "result_summary":  "What was delivered..."
}

# 4. Synthesize (required for M/L/XL)
POST /work-synthesize {
  "work_item_id": "uuid",
  "body":         "Lessons: ... Follow-on items: ... Pattern note: ..."
}

An agent that calls these endpoints is following the protocol by doing the work. No separate SKILL document required beyond this PRD. The protocol is the API.

07 · Interface

Three views. One auth gate.

The interface lives at /intranet/activity/ — auth-gated by the same Supabase session gate as /intranet/treasury/ and /intranet/board/. Three tab views query the same underlying data.

View 1 · Feed (default)

Reverse-chronological list of work events. Each row: phase pill, event_type label, actor name and type badge, subject_ref with link to work item or GitHub artifact, title, relative timestamp. Filter bar: phase, actor_type, event_type, subject_type. Virtual scroll, no pagination UI. This is the answer to "what has been happening?"

View 2 · Work Items

The active work item board — not a Kanban, a list. Grouped by phase (Proposal → Negotiation → Execution → Testing → Synthesis). Each item shows: ref (W042), title, assignee, complexity, last event timestamp. A member can propose a new work item from this view. An agent can claim an open item. This is the answer to "what can I work on next?"

View 3 · Coverage

The address space is already mapped. techne.institute/tree is the live navigator of the full domain — six access zones (Home, Public, Curated, Members, Steward, Discovered), three navigation modes (List, HUD, Network), and a force-directed graph of page relationships. Coverage does not rebuild this. It annotates it.

In Phase 3, work event data flows from this ledger into the tree. Each node in the address space gains: event count in the selected window, distinct actors, last-touched date, phase of most recent event. Nodes with no recent events acquire a staleness signal — configurable per path prefix (90 days for /cis/, 30 days for /intranet/). The Coverage tab opens the tree in an annotated mode filtered to any time window. The question "which parts of the address space haven't been maintained?" becomes answerable directly from the tree, without a separate tool. Phase 3 only.

Design notes

Techne design system throughout: dark void at var(--void) (#0c0c0c), IBM Plex Mono for all data labels, gold accent sparingly. Phase pills use the five-color system from this document. No charts with axes — a ledger, not an analytics dashboard. Numbers are counts, not metrics.

08 · GitHub Integration

One webhook handler. Normalization, not interpretation.

A single Supabase Edge Function — work-github-ingest — receives GitHub webhook events from all tracked repositories and normalizes them into work_events. It does not create work items; it only creates events. The link between a GitHub event and a work item is established by including a work item ref (W042) in the commit message or PR body — or retroactively by a steward via actor_reconciled.

GitHub Eventwork_event typePhase inferredwork_item link
pushgit_pushexecutionFrom commit message "W042" pattern
pull_request.closed (merged)pr_mergedexecutionFrom PR title or body "W042" pattern
issues.closedissue_closedsynthesisFrom issue body "closes W042" pattern

Actor matching

GitHub username is matched against a github_username column on the participants table. Unmatched events are written with actor_id null and actor_name from the webhook payload. A steward-facing reconciliation panel in /intranet/activity/ shows unmatched events and allows actor assignment.

Tracked repositories

Webhooks are configured per GitHub organization. The initial scope covers RegenHub-Boulder and any additional orgs holding Techne-affiliated work. The webhook list is defined before Phase 2 begins — not discovered incrementally — to avoid partial coverage creating misleading feed gaps.

Deduplication

The unique index on (source, source_id) makes webhook delivery idempotent. A duplicate delivery writes nothing and returns 200. No retry logic required in the handler.

Migration from the Workshop

Phase 1 includes migrating the active coordination workflow for Nou and Dianoia from co-op.us/app/coordinate to the CIS Coordination API. Historical Workshop records are not migrated — they remain in the co-op.us Supabase project as an archive. The Work Ledger begins with a clean event log on first deployment. Open work items in the Workshop at migration time are re-proposed in the new system by the responsible agent.

10 · Open Questions

What we do not yet know.

Approval threshold for self-complete

Which item sizes require steward review before close?

The PRD proposes XS/S items may self-complete; M/L/XL require steward approval. The right threshold depends on how frequently stewards are available and how much latency is acceptable. A fully-autonomous agent needs to be able to complete XS sprints without a human review step — otherwise it blocks on availability. This decision should be made before Phase 1 ships and encoded in the /work-complete endpoint logic.

participants.github_username

The column may not exist yet

Actor matching for GitHub events requires a github_username field on the participants table. If it does not already exist, it must be added as part of the Phase 2 schema migration. For agents (Nou, Dianoia), the match is by a configured constant rather than a GitHub username — agents commit via a configured git identity that maps directly to their participant record.

Governance events in Activity

Where do meeting records, votes, and notices live?

The CIS PRD v0.2 lists Activity as: "Meetings, votes, notices, consent requests, state changes." The Work Ledger covers state changes and work items. Meeting records, votes, and notices are distinct entity types not covered by work_items — they need their own tables and are potentially a separate sub-section of /intranet/activity/. This PRD does not specify them; they should be specified before Phase 1 ships to avoid an interface that implies completeness it does not have.

Work item numbering

W001 or a continuation of P-numbers?

The Workshop used P-numbers (P486, P496). The Work Ledger proposes W-numbers (W001). The choice matters for backward references in commit messages and documentation. If the cooperative intends to maintain a continuous history reference, continuing the P-series (or a new series that encodes the source system change) may be cleaner than starting a parallel numbering. This is a convention decision, not a schema decision, but it should be made before Phase 1 to avoid renaming later.

The Workshop taught this cooperative something that cannot be un-learned: coordination is not communication. Talking about work and recording work are different acts. A system that conflates them — that treats a message as a state transition — will always drift toward noise.

The Work Ledger separates them cleanly. The API handles state. The feed surfaces it. The chat, wherever it lives, is the conversation layer alongside both — not a substitute for either. A cooperative that can answer "what did we make together?" and "what are we making now?" from a single source has the minimum viable infrastructure for collective intelligence.
